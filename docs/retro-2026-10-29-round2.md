## 1. 自动化检查（最高优先级）

**事实**：本轮之前，仓库里 `npm run build` 会跑 `tsc`，`npm test` 有 584 个用例，
`npm run ui:check` 也能跑——但三者**都没有接到任何自动触发点上**。改完代码是否通过，全靠人记得跑。
这不是「缺工具」，是「工具悬空」。

**已做**：接入 husky（`core.hooksPath=.husky/_`），pre-commit 跑类型 + 相关单测 + 反模式静态扫描，
pre-push 跑全量单测 + 完整 UI 回归。

**残留问题**：`tools/preview_multisize.py`（界面冒烟）仍只能手动跑，且依赖本机能起 Playwright。
它是目前唯一能发现「界面炸了但类型/单测全过」的检查，建议下一步纳入 pre-push（`--no-build` 复用 dist，约 20s）。

## 2. 导航

**事实**：`docs/` 已有 13 篇文档，彼此靠正文互相引用；`IdPhoto.tsx` 2,075 行，
一次「找导出逻辑在哪」要 grep 三四个关键词（`exportAll` / `buildPersonLayer` / `compositeLayer`）
才能定位到 744-858 与 770-845 两处。

**建议**（都很便宜）：
1. 建 `docs/INDEX.md`：一行一篇，按「规格构图 / 批量性能 / 打包 / UI 门禁 / 产品调研」分组。
2. 建仓库根 `AGENTS.md`，只放导航指针，不写规范：
   - 打包只走 `npm run pack`（输出 `dist-pkg-current`，会自动清空）
   - 门禁命令：`npm run typecheck` / `npm test` / `npm run ui:check`
   - 文档索引见 `docs/INDEX.md`
   这三条恰好是每次冷启动都要重新解释的内容，属于典型「该进指针文件」的信息。

## 3. 编码规范

**事实**：本轮唯一真正踩到的结构性错误是「合成管线写了两遍」——预览 effect 与导出各一份，
上一轮 `zoom` 丢失就是这么来的。这类「同一段参数合并逻辑复制两处」的问题，任何 linter 都抓不到，
但**评审可以**。

**建议**：把这条写成一条评审规则（不是 lint 规则）：**同一组参数在两条代码路径里各拼一次 → 必须抽函数**。
放在 `CODING_STANDARDS.md`（若建）里，属于判断类，不适合作自动检查。

## 4. 工具经济性

**事实**：本轮跑 impeccable 时，第一次用了 `detect src` 的文本输出（几百行、每条带长解释），
后来才知道 `--json` 才适合程序消费；同类问题在 `pack` 上已经吃过一次（日志刷屏）。
另外 `npm run ui:check` 默认会构建（约 25s），反复调试时应该先 `ui:check:fast`。

**建议**：在 `AGENTS.md` 的导航里补一句「机器读用 `--json`，人读用默认输出」，
并把 `ui:check` / `ui:check:fast` 的取舍写进 `docs/ui-regression.md`（已补）。

## 5. 信息获取

**事实**：这台机器上 Electron GUI 起不来（二进制被替换），所以「程序长什么样」只能靠
`tools/preview_multisize.py` 起 Playwright 看。本轮做配色整改时，改完只能看
「对比度数值达标」，看不到「深了一档的灰是否影响层次」——这是本次唯一没有自动化的判断环节。

**建议**：给 `preview_multisize.py` 加个 `--shot` 参数，把首页整页截图存到 `.tmp/shots/`，
改配色时前后各拍一张，人眼对比 30 秒即可，比反复描述颜色可靠。

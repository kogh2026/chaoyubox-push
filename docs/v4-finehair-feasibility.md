## 0. 结论前置（三个问题直接回答）

| 你的问题 | 判定 | 一句话理由 |
|---|---|---|
| 自己用，@imgly 有授权风险吗？ | ✅ **没风险** | AGPL 的义务（附源码）只在「把软件分给别人」时触发。你自己编译、自己用、不分发 → 不触发任何义务 |
| 目前超誉用的（@imgly + 其余依赖）有风险吗？ | ⚠️ **@imgly 没问题，但另有真雷** | 依赖扫描：除 @imgly 外全是 MIT/Apache-2.0，jszip 是「MIT 或 GPL」双授权（选 MIT 即可）。**真正的雷是 `resources/card-model/card-correction-fp32.onnx`——它是爱印商业软件的解密产物**（SHA 前缀 `bbf5b9b2`），这跟"自用"无关，是另一类问题，见 §1.3 |
| @imgly vs 换开源模型，哪个效果好？有对比性吗？ | ✅ **有，且数字明确** | 公开 benchmark 上 BiRefNet 明显更强（发丝边缘 HCE 改善 23.8%）；但**在本机 4 核 CPU 上它跑不动**，且它的授权不如想象中干净。**最优解是路径 D：保留 MIT 授权的 ISNet 权重、自己写推理，甩掉 @imgly 代码，效果一模一样** |

**一句话总结：授权这件事自用无虞；真正该做的是"用 MIT 权重自己推理"（路径 D）——既保持现有效果、又把 AGPL 依赖彻底摘掉，比换模型代价小得多。**

## 1. 授权这件事，说人话

### 1.1 `@imgly/background-removal@1.7.0` 到底是什么授权

- 包内 `LICENSE.md` 原文 = **GNU AGPL v3 全文**（34KB）。上一版文档写的"GPLv3 + 商用授权双轨"措辞不准：AGPLv3 是这个包自带的授权；IMG.LY 官网另外单卖一份商业授权，是**替代选项**，不是叠加。
- 包内 `ThirdPartyLicenses.json` 声明的第三方组件：

  | 组件 | 类型 | 授权 |
  |---|---|---|
  | onnxruntime-web | 代码 | MIT |
  | **ISNET**（github.com/xuebinqin/DIS） | **模型权重** | **MIT** |

### 1.2 自用 vs 分发（这是关键分界线）

| 使用方式 | 触发 AGPL 义务吗 | 说明 |
|---|---|---|
| **自己编译、自己用、只跑在本机** | ❌ **不触发** | AGPL 的源码提供义务只在「conveying（分发/传播）」时发生。自己用 = 无分发 = 无义务 |
| 把打包好的 exe 发给朋友 / 同事 | ✅ **触发** | 哪怕免费、哪怕非商业分发，AGPL §6 也要求附上完整对应源码 + 保留版权声明 |
| 放在公司内部多人共用 | ⚠️ 边界情况 | AGPL §13 是网络服务条款（桌面应用不适用）；内部使用一般不算分发，但要看具体形态 |
| 公开上架 / 售卖 | ✅ **触发** | 同上，商业分发必须满足 AGPL 或改买商业授权 |

> AGPL §13（网络交互）针对的是"用户通过网络与你的修改版交互"，桌面离线应用不适用。
> **所以：你的判断是对的——自用没有风险。** 但它是一颗定时炸弹：哪天你想把超誉发给别人/上架，必须先处理它。

### 1.3 ⚠️ 真正的雷不是 @imgly，是爱印解密模型

| 项 | 事实 | 风险 |
|---|---|---|
| `resources/card-model/card-correction-fp32.onnx` (41.4MB) | SHA 前缀 `bbf5b9b22c4142c5`，与 `aiyin_models_decrypted/` 里的**爱印商业软件解密件完全一致** | 🔴 **高**。这是从他人商业产品里提取的专有权重，著作权归属不明。自用不传播 = 实际执法风险低；但**一旦分发，问题比 @imgly 严重得多**（AGPL 是有明确合规路径的开源许可证，专有模型权重是"拿人家的东西"） |
| `aiyin_decrypted_assets/` / `aiyin_models_decrypted/` | 逆向产物，**在仓库外**，且不在 `build.files`/`extraResources` 范围 | ✅ 不会被打进安装包。**保持现状即可，不要挪进 `resources/`** |
| 仓库根目录 | **无 LICENSE / NOTICE / 第三方声明文件** | 🟠 中。一旦对外分发，需要一份汇总声明（第三方组件 + 各模型权重出处与授权） |

**处置建议（按优先级）**：
1. 卡证矫正模型：**继续自用没问题**；若将来要分发，改为自训权重或换公开授权模型（这是独立课题，不在 V4 范围）。
2. 在 `resources/` 里加一份 `MODELS.md`，逐个写清权重来源与授权（ISNET=MIT、MODNet=Apache-2.0、卡证矫正=来源待定/仅内部）。
3. 待产品形态确定（自用 / 内部分发 / 对外销售）再决定是否买 @imgly 商业授权——**现在不需要**。

## 2. 效果对比：到底哪个好？（有数字）

### 2.1 公开 benchmark（DIS5K / HRSOD / COD 抠图标准集）

| 数据集 | 指标 | IS-Net（@imgly 现在用的） | BiRefNet | 变化 |
|---|---|---|---|---|
| DIS5K | F-measure ↑ | 0.761 | **0.799** | **+5.0%** |
| DIS5K | MAE ↓ | 0.083 | **0.070** | **−15.7%** |
| DIS5K | HCE ↓（发丝边缘人工修正量） | 1333 | **1016** | **−23.8%** |
| HRSOD | MAE ↓ | 0.020 | **0.014** | −30.0% |
| COD | F-measure ↑ | 0.806 | **0.874** | +8.4% |

> **读法**：BiRefNet 在发丝边缘（HCE）上的优势最明显——HCE 就是"人要手工修多少像素"，正好对应"发丝完整度"。所以**天花板确实更高**。

### 2.2 但在这台机器上，跑不动就是零

本机：**4 核 CPU / 16GB 内存 / 无独显**。项目已有第一方实测（`.tmp/bench-batch50/`，50 张证件照）：

| 引擎 | 50 张总耗时 | 单张 | 权重体积 | 离线 |
|---|---|---|---|---|
| ISNet fp16（=「精细」） | 288 s | **5,759 ms** | 84.1 MB | ✅ 包内已带 |
| MODNet（=「快速」） | 45 s | **894 ms** | 25 MB | ✅ 包内已带 |

ISNet 比 MODNet 慢 **6.4 倍**。而 BiRefNet general 是 **2.21 亿参数**（safetensors 444.5MB，桌面 ONNX 导出版约 200–450MB，视精度/版本而定），比 ISNet（8400 万参数级）重一个量级——**在 4 核 CPU 上跑 BiRefNet 会比现在的 ISNet 还慢数倍**，批量场景不可用。

### 2.3 另一个关键情报：rembg 500 张实测

第三方在 AIM-500（500 张人工标注 alpha）上的实测结论值得抄作业：

| 模型 | 结果 |
|---|---|
| **ISNet + ViTMatte 边缘精修** | 所有免费方案里**误差最低**（比 ISNet 单独用再降约 21%） |
| u2net | 最快（0.12s/张），但发丝一般 |
| **RMBG-2.0** | ❌ **CC BY-NC 4.0 非商用**，且 12GB 机器上直接 OOM（峰值 6.9GB 被杀） |

**这条情报同时说明两件事**：
- 「ISNet 打底 + 轻量模型只精修边缘」是**被验证过的最优性价比组合**——正好就是我们的**路径 C**。
- **RMBG-2.0 授权比 @imgly 还差**（非商用 vs 有合规路径），v1 把它当"授权干净的开源模型"是错的。

## 3. 现有能力盘点（缺什么）

| 已有 | 位置 |
|---|---|
| 双引擎 `isnet`/`modnet`，默认 modnet | `src/lib/matteEngine.ts:9-22` |
| UI「精细 / 快速」二选一 + ≥10 张耗时预警 | `src/tools/IdPhotoRight.tsx:316-317, 24` |
| 发丝后处理：`edgeThreshold` + `defringeOn` | `src/lib/idphotoOptions.ts:58-61`、`src/lib/matting.ts:81-135` |
| Worker 池 + 缓存 + 空闲卸载 | `src/lib/mattingPool.ts`、`src/lib/idleUnload.ts` |

**真实缺口**：
1. **没有模块边界**：`isnet` 只是枚举里的一个分支，无法单独交付/灰度/关闭/换模型。
2. **回退不一致（已知 bug）**：主线程兜底 `matte()` 恒用 ISNet（`mattingPool.ts:192` 注释自陈"切快速也不生效"）→ "快速"档在回退场景其实失效，精细发丝反而恒开。
3. **没有发丝专用模型**：ISNet 是通用抠图，发丝是顺带做得好。
4. **没有质量分级**：只有"精细/快速"二值。
5. **底座与授权缠在一起**：`isnet` 分支的推理代码在 AGPL 包内（权重本身是 MIT）。

## 4. 四条路径

### 路径 A —— 包装复用（零新模型，最快）
把现有 `isnet` 从"引擎分支"升级为独立模块：独立 UI 入口、独立缓存命名空间、独立开关与分级（标准/增强/极致，仍复用 ISNet），并修回退不一致。

- 工作量：小。质量天花板：受限于 ISNet。风险：低。

### 路径 B —— 换开源模型（天花板最高）
换成面向人像/发丝优化的开源模型。

| 候选 | 授权 | 体积 | 本机 4 核 CPU 可行性 |
|---|---|---|---|
| **BiRefNet**（general / lite2k / portrait） | ✅ **MIT**（代码+权重） | 约 200–450MB（视导出精度） | ❌ 慢一个量级，批量不可用；可做"单张极致"档 |
| **RMBG-2.0** | ❌ **CC BY-NC 4.0 非商用** | — | ❌ 12GB 机器 OOM（第三方实测） |
| **ViTMatte** | ✅ 代码 MIT / 权重 Apache-2.0 | 约 100MB（26M 参数） | ⚠️ 需 trimap，不能独立抠图 |

- 优势：发丝上限最高。代价：模型体积、内存、CPU 速度、**需要重做一轮难例基准**。

### 路径 C —— 两阶段：base 快抠 + 发丝精修（性价比最优）
用 MODNet（快）/ ISNet 出主体 mask，再用一个**轻量发丝精修模型**只修边缘过渡带（ViTMatte 类）。只动边缘带 → 精修本身便宜。

- 优势：在现有速度上把发丝补回来；**已被 rembg 500 张实测验证有效**（ISNet+ViTMatte 误差最低）。
- 代价：管线多一段（边缘带提取 → trimap 生成 → 精修 → 合成），需处理接缝避免"双重边缘"。
- 风险：中（接缝/合成伪影）。

### 🆕 路径 D —— 自研 ISNet 推理，甩掉 @imgly（**新增，最推荐**）

**核心洞察**：@imgly 的 ISNet 推理逻辑极简单，我们已经完整摸清，可以自己写：

```
输入解码 → 双线性 resize 到 1024×1024（不保长宽比）
        → HWC 转 BCHW，均值 [128,128,128]、方差 [256,256,256]
        → onnxruntime-web 推理（输入名 input / 输出名 output）
        → 输出已是 sigmoid 后的 alpha → 转 uint8 → resize 回原图尺寸
```

**为什么这条路最优**：
- **授权归零**：ISNet 权重是 MIT（DIS 仓库）、onnxruntime-web 是 MIT → 我们自己写的胶水代码是自己的，**AGPL 依赖直接消失**。
- **效果零损失**：同一份权重、同一套预处理 → 像素级应当一致，可用现有 `tools/matting.quality.cjs` 做回归比对。
- **成本最低**：MODNet 的自研推理已经在 `matting.worker.ts:96-142` 跑通了（同样的 ORT + OffscreenCanvas + 归一化套路），照抄一份即可。
- **顺带简化**：@imgly 那套「CDN / IndexedDB / 分片下载」我们本来就要用 `appres://` 自己那套（`resources/matting-model/` 22 个分片已在包内、离线可用），自研后可以直接读本地分片，少一层依赖。

**注意一个易错点**：ISNet 的归一化是 `(x−128)/256`，**与 MODNet 的 `(x/255)*2−1` 不同**。自己实现时必须照抄 @imgly 的常量，否则发丝质量会掉。

## 6. 集成边界（沿用 v1，补充 D 的落点）

- **接入点**：`matte()` 出透明 PNG 之后、`buildPersonLayer()`（`src/lib/matting.ts:360`）之前；或在 `mattingPool` 引擎分支里单独成路。**不动「快速」路径**。
- **缓存**：精细发丝结果要**独立命名空间/指纹**，避免与快速结果串缓存；`matteCache` 已是 BoundedCache，支持 `deletePrefix` 级联清理。
- **内存**：`MAX_MATTE`（`mattingPool.ts:40-49`）按每 Worker ≈300MB 封顶。引入第二模型时**不要两个模型常驻同一 Worker**；推荐精细模块独占一组 Worker 或按需懒加载 + 空闲卸载（复用 `idleUnload.ts`）。
- **线程配额**：`matteThreads()`（`mattingPool.ts:65-67`）"并发度 × 线程数 ≈ 核数"，模块接入直接复用。
- **回退一致性（必修）**：模块化时必须让主线程回退也尊重"快速/精细"选择，否则快速档在回退场景失效。
- **选项 Schema**：在 `PhotoOptions`（`src/lib/idphotoOptions.ts`）加 `hairFine: 'off'|'std'|'enh'|'ultra'`；保持"影响产出的配置才入 options"的既有边界。
- **路径 D 专属**：自研推理放 `src/lib/mattingIsnet.ts`（与现有 `matting.worker.ts` 的 MODNet 实现并列），`matting.worker.ts` 里 `engine==='isnet'` 分支改为调用它；`cardDetectMl.ts` 里那个 `@imgly` 动态 import 一并替换（否则 AGPL 仍会被打进包）。

## 7. 资源与风险

| 风险 | 等级 | 说明 / 缓解 |
|---|---|---|
| **爱印解密模型权重** | 🔴 高 | 与分发相关，自用无碍。**缓解：不定性为分发场景；对外分发前必须替换或取得授权** |
| **AGPL 依赖** | 🟠 中→🟢 | 自用无碍，分发前必须处理。**缓解：走路径 D 直接摘掉**（本是最优解） |
| 性能 / 批量卡顿 | 🟠 中 | ISNet 5.8s/张。**缓解：沿用耗时预警 + 一键切快速；路径 C 几乎不掉速** |
| 内存 | 🟠 中 | 每 Worker ≈300MB。**缓解：独占/懒加载 + 空闲卸载** |
| 自研推理与 @imgly 不一致 | 🟡 低 | 归一化常量照抄即可。**缓解：用 `tools/matting.quality.cjs` 做像素级回归（同一张图两路输出比 alpha IoU / edgeDiff）** |
| 精度回归 | 🟠 中 | 帽子/辫子/白发/眼镜难例。**缓解：难例评测集 + 人工抽检** |
| 缺第三方声明 | 🟠 中 | 无 NOTICE。**缓解：加 `resources/MODELS.md`** |

**资源**：路径 D 零新模型、零新增体积；路径 C 需新增约 100MB 轻量精修权重 + 一套 `appres://` 托管；路径 B 需 200–450MB 权重 + 内存重估。

## 8. 推荐方案

**推荐：D 打底（阶段 1）→ C 提质（阶段 2）→ B 作为可选"极致"档（阶段 3）**

- **阶段 1（V4 内）— 路径 D + 模块骨架**
  - 自己实现 ISNet 推理（`mattingIsnet.ts`），用包内已有的 MIT 权重 → **AGPL 依赖归零**，效果不变；
  - 抽 `hairFine` 模块壳（独立开关、独立缓存命名空间、分级）；
  - 修主线程回退不一致；
  - 加 `resources/MODELS.md` 第三方声明；
  - 验收：与 @imgly 输出像素级一致（`matting.quality.cjs` 回归）、模块可单独开/关、快速档回退生效。
- **阶段 2（V4.x）— 路径 C**：加轻量发丝精修（ViTMatte 类，Apache-2.0），只修边缘带，把发丝质量拉高一档，速度几乎不掉。
- **阶段 3（可选）— 路径 B**：`BiRefNet`（MIT）作为"单张极致"档，只在用户明确要求时加载；接受它在本机很慢。

**验收总标准**：难例评测集上发丝边缘 HCE/IoU 提升、换底彩晕率下降、批量耗时预估准确、模块可灰度、**安装包内不再含 AGPL 代码**。
